# Hermes и Kubernetes: предпосылки проектирования

Проверено 2026-09-18 по первичным источникам. Первый проход сделан по изменяемой ветке `main`; во втором проходе зафиксированы `main` SHA `01382698fc32ec7740b6a204d9b7a6abeac74d33` и release image revision `345cd2b057a452236de401d3534b8502a7465e8d` для `v2026.9.14`. Это исследуемые версии, а не уже принятый контракт поддержки. Контейнерные и кластерные испытания не выполнялись: ниже документированные свойства и выводы для проектирования.

## Hermes

1. Официальный образ оставляет `USER root`: s6 стартует с root и затем понижает UID сервисов. Это требует проверки или адаптации для строгого запуска `runAsNonRoot`, но не доказывает невозможность такого запуска. [Dockerfile](https://github.com/NousResearch/hermes-agent/blob/main/Dockerfile#L283-L297), [entrypoint](https://github.com/NousResearch/hermes-agent/blob/main/docker/entrypoint-dispatch.sh#L15-L22).
2. Workspace и состояние агента различаются. `terminal.cwd` задаёт рабочий каталог, а `HERMES_HOME` объединяет config, credentials и изменяемые sessions, memories, skills, cron и другие данные. PVC только для workspace не сохраняет всё состояние; запрет записи во весь home мешает штатной работе. [Docker storage](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/docker.md), [configuration](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/configuration.md).
3. Telegram предоставляет переключение модели; reasoning также можно менять внутри сессии без сохранения config. Есть разграничение административных и пользовательских slash-команд, однако оно не является изоляцией произвольного кода в инструментах агента. Необходимо проверить все пути изменения эффективной конфигурации. [Telegram commands](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/telegram), [reasoning configuration](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/configuration.md#L1542-L1553).
4. Встроенный dashboard редактирует настройки и credentials и предоставляет административные возможности. Его нельзя автоматически считать подходящим пользовательским интерфейсом при запрете изменения настроек. Документированы username/password и OAuth/OIDC; модель доступа не следует заранее сводить к одному bearer token. [Web dashboard](https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard).
5. Telegram по умолчанию использует исходящий long polling; публичный endpoint для этого режима не нужен. Также существует webhook-режим. ID отправителя и ID группового чата задают разные правила доступа, поэтому в API их нужно различать. [Telegram](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/telegram).

## Изоляция и сеть

1. Обычные контейнеры используют ядро узла. Для недоверенного или вредоносного кода Kubernetes рекомендует рассмотреть sandbox с VM или userspace kernel. Non-root и Restricted Pod Security полезны, но не заменяют эту границу. [Multi-tenancy](https://kubernetes.io/docs/concepts/security/multi-tenancy/#sandboxing-containers), [Restricted PSS](https://kubernetes.io/docs/concepts/security/pod-security-standards/#restricted).
2. NetworkPolicy требует реализации со стороны CNI; разрешения разных политик складываются. Документация отдельно оговаривает трафик к/от hosting node и зависимость обработки NAT от реализации. Поэтому наличие default-deny и списка исключений само по себе не доказывает запрет доступа ко всей инфраструктуре. [NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/).
3. Запрет только RFC1918 недостаточен для заявленной цели. Требуют рассмотрения специальные IPv4/IPv6 диапазоны, link-local/metadata, фактические сети Pod/Service/node, публичные адреса инфраструктуры и разрешённые DNS-серверы. Конкретные правила зависят от выбранной среды. [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/), [IANA IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry/), [Kubernetes DNS isolation](https://kubernetes.io/docs/concepts/security/multi-tenancy/#dns).
4. Ссылка на Secret не скрывает выданные процессу credentials от кода, который способен читать то же окружение или файлы. Вывод для дизайна: если ключ должен быть скрыт даже от владельца агента, необходима отдельная проверяемая граница исполнения или выдачи credentials. [Secrets practices](https://kubernetes.io/docs/concepts/security/secrets-good-practices/).
5. Pod агента может работать без автоматически смонтированного API token: `automountServiceAccountToken: false`. Само использование Secret/PVC не требует выдачи приложению доступа к Kubernetes API. [ServiceAccount](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/#opt-out-of-api-credential-automounting).
6. При HTTPRoute нужно учитывать разрешение attachment со стороны Gateway, cross-namespace references и владение hostname. Эти разрешения ресурсов не заменяют пользовательскую аутентификацию UI. [Gateway API security model](https://gateway-api.sigs.k8s.io/docs/concepts/security/).

## Текущее архитектурное решение

Пользователь выбрал стандартные механизмы Kubernetes без Kata/gVisor, доверенных создателей CR/Secrets и выделенные credentials, доступные изнутри собственной инсталляции. Внешний backend, web UI и HTTPRoute не входят в первый релиз. Последнее уточнение допускает writable runtime config и временную смену модели: CR/Secret-параметры восстанавливаются перед каждым запуском, персонализация и данные остаются на PVC. Read-only managed overlay и блокировка команд смены модели больше не являются выбранной архитектурой.

## Уточнения для второго раунда

- Официальный registry repository существует: [nousresearch/hermes-agent](https://hub.docker.com/r/nousresearch/hermes-agent/). Собственная сборка сейчас не является необходимой предпосылкой.
- При монтировании config/Secret отдельными файлами через `subPath` обновления исходного ConfigMap/Secret не поступают в существующий mount автоматически. Для такой схемы потребуется пересоздание Pod при изменении конфигурации или credentials. [ConfigMaps](https://kubernetes.io/docs/concepts/configuration/configmap/), [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/).
- Telegram sender allowlists и group allowlists означают разные вещи. `group_allowed_chats` может разрешать всех участников группы. Пустой `allowed_chats` нельзя принимать за запрет групп: это отсутствие соответствующего ограничения. Матрицу разрешений нужно проверить на выбранной версии. [Telegram docs](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/telegram.md), [adapter](https://github.com/NousResearch/hermes-agent/blob/main/plugins/platforms/telegram/adapter.py).
- Один bot token предполагает одного активного long-polling consumer; несколько процессов могут получить Telegram `409 Conflict`. Одна реплика StatefulSet соответствует штатному одиночному запуску. `Deployment/Recreate` ограничивает overlap при upgrade, но не даёт такого же поведения при ручном удалении Pod. При force-delete и сетевом разделении нельзя обещать абсолютный singleton. [Deployment Recreate](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#recreate-deployment), [StatefulSet force-delete](https://kubernetes.io/docs/tasks/run-application/force-delete-stateful-set-pod/).
- `ReadWriteOnce` означает один узел, а не строго один Pod. `ReadWriteOncePod` имеет более строгую семантику и требует поддержки CSI. [Access modes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes).
- Сохранение PVC после удаления CR требует правильных ownerReferences/retention. Оно не эквивалентно PV reclaim policy `Retain`, которая относится к судьбе underlying storage после удаления PVC. Подключённый существующий PVC предлагается считать внешним ресурсом. [Owner references](https://kubernetes.io/docs/concepts/overview/working-with-objects/owners-dependents/), [PVC retention](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#persistentvolumeclaim-retention), [PV reclaiming](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#reclaiming).

## Проверка неизменённого upstream

На этом этапе не выявлено доказанной необходимости изменять исходники Hermes. Проверка кода и registry не заменяет smoke-тест образа.

- Проверенный официальный multiarch image: `nousresearch/hermes-agent:v2026.9.14@sha256:99641e57ec762c59e54cb44aa6746b7fc68c18b3c5ddb088af54234c613d9294`, платформы `linux/amd64` и `linux/arm64`. Значение зафиксировано из registry metadata; образ не скачивался и не запускался. [Tags](https://hub.docker.com/r/nousresearch/hermes-agent/tags), [publish workflow](https://github.com/NousResearch/hermes-agent/blob/01382698fc32ec7740b6a204d9b7a6abeac74d33/.github/workflows/docker.yml#L302-L340).
- Кандидат для запуска без root — `/opt/hermes/.venv/bin/hermes gateway run --no-supervise` с UID 10000 и writable `HERMES_HOME=/opt/data`. Это обходит s6 и его boot chown/seeding; нужные каталоги и начальное состояние придётся подготовить отдельно. Совместимость с read-only root filesystem и mounts ещё не проверена запуском. [Gateway CLI](https://github.com/NousResearch/hermes-agent/blob/01382698fc32ec7740b6a204d9b7a6abeac74d33/hermes_cli/gateway.py#L6024-L6032).

Ближайшая техническая проверка: закреплённый официальный образ под UID 10000, writable PVC/config, применение эталонных параметров перед каждым запуском; затем персонализация, смена модели, restart контейнера и проверка возвращения CR-модели в прежней беседе с сохранением всех пользовательских данных. См. [startup restore](startup-restore.md).

После второго раунда уточнены [mapping основных полей и реальные Telegram group gates](config-mapping.md). Generic `group_policy: disabled` не следует использовать как доказательство работы режима DM-only.

## Ранее исследованные ограничения runtime config

Эти механизмы проверялись при прежнем требовании read-only настроек. Они оставлены как справочные факты об upstream; применять managed lock или запрет смены модели для текущей архитектуры не требуется.

- В release уже есть managed scope: `/etc/hermes/config.yaml` перекрывает пользовательский config по ключам, `/etc/hermes/.env` загружается последним. Неуказанные параметры не становятся автоматически управляемыми. Ошибка чтения managed config обрабатывается fail-open, поэтому конфигурацию необходимо валидировать до запуска. [Managed scope](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/hermes_cli/managed_scope.py#L116-L143), [env loader](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/hermes_cli/env_loader.py#L423-L438).
- Отдельный `HERMES_MANAGED` ограничивает обычные операции сохранения config, но не заменяет read-only mounts. Полное дерево home должно оставаться writable для SQLite `state.db`/WAL/SHM, skills, memory, cron, sessions и других рабочих данных. [State DB](https://github.com/NousResearch/hermes-agent/blob/01382698fc32ec7740b6a204d9b7a6abeac74d33/hermes_state.py#L161-L181), [home initialization](https://github.com/NousResearch/hermes-agent/blob/01382698fc32ec7740b6a204d9b7a6abeac74d33/hermes_cli/config_home.py#L55-L73).
- Пустой `allow_admin_from` не запрещает административные команды: ограничение включается только при непустом списке. Документированная схема использует доверенный Telegram admin ID, а пользователи вне этого списка ограничиваются allowlist команд. Проверка release-кода также выявила альтернативу: непустой служебный строковый маркер, который не может совпасть с числовым Telegram user ID. Это недокументированный конфигурационный приём, не реальный Telegram ID; он требует integration smoke и не считается уже принятым контрактом. Для групп существует отдельная настройка. [Slash access release](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/gateway/slash_access.py#L38-L93).
- В release `v2026.9.14` обработчики `/model` и `/reasoning` не проверяют managed scope. Даже отказ записи readonly config при `/reasoning --global` не препятствует session override. Поэтому необходима отдельная проверка запрета этих команд через slash policy; одного managed config недостаточно. Отдельного глобального параметра `disabled_commands`/`enabled_commands` при проверке gateway/Telegram defaults и обработчиков не найдено. [Model](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/gateway/slash_commands_model.py#L139-L169), [reasoning](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/gateway/slash_commands_model.py#L582-L614), [dispatch guard](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/gateway/run_busy.py#L967-L975).
- Read-only конфигурация защищает управляемые файлы, а не запрещает пользователю с shell и доступными credentials запустить свой API-клиент или дополнительный процесс с другими настройками. Проект не должен подменять одно обещание другим. [Environment precedence](https://github.com/NousResearch/hermes-agent/blob/01382698fc32ec7740b6a204d9b7a6abeac74d33/hermes_cli/env_loader.py#L376-L460).
