# Веб-доступ к инсталляции Hermes

Дата: 2026-09-28. Статус: контракт подтверждён пользователем; реализация разрешена 2026-09-28.

Это продолжение [исходного интервью](interview.md): веб-интерфейс и HTTPRoute были
отложены в первом релизе и теперь запрошены как отдельное расширение оператора.
Остальные принятые границы сохраняются, включая [неизменённый upstream](../adr/0002-upstream-and-security-boundary.md)
и [восстановление управляемых настроек при запуске](../adr/0001-declarative-configuration-authority.md).

## Требования из нового запроса

- Веб-доступ по умолчанию выключен; для включения нужны явные настройки CR.
- Запрошены два способа адресации: отдельный домен инсталляции
  (`hermes1.agents.s2technologies.ru`) и отдельный путь общего домена
  (`agents.s2technologies.ru/hermes1`). Поддержка пути требует проверки самого Hermes,
  включая frontend, API, WebSocket и хранение браузерной сессии.
- В CR задаются базовый домен, способ адресации и используемый Kubernetes Gateway.
  Предлагаемый набор полей приведён в инженерном контракте ниже.
- Credential для входа должен быть доступен администратору в основном Secret
  инсталляции. Запрошено рассмотреть автоматическую генерацию и явное задание.
  Название ключа и форма credential зависят от проверенного механизма upstream.
- Вся функция, её настройки, эксплуатация и ограничения должны быть задокументированы.
- Кластерная проверка проводится на существующей тестовой инсталляции в `berger-apps`.
  Пересоздание пользовательского состояния не запрошено.

## Принятые ответы

- Q1: полный штатный веб-интерфейс Hermes, включая доступные в нём настройки,
  файлы и управление собственной инсталляцией. Сохраняется правило восстановления
  управляемой конфигурации из CR/Secrets при рестарте.
- Q2: оператору разрешено добавлять credential в основной Secret
  (`<имя>-hermes-secret` или `credentials.secretName`). Явно заданное значение
  используется; отсутствующее генерируется однократно. Другие ключи не изменяются,
  рестарты сами по себе не меняют credential. Точные ключи, механизм входа и
  ротация конкретизированы в предлагаемом инженерном контракте ниже.
- Q3: Telegram перестаёт быть обязательным. Один CR допускает Telegram, Web,
  оба канала или отсутствие обоих. Требование «хотя бы один включён» отвергнуто.
  Без каналов инсталляция не имеет пользовательского способа подключения на этом
  этапе; runtime-поведение, фоновые задачи и readiness в таком режиме ещё проверяются.
  Существующие Telegram CR должны продолжать работать с прежним смыслом.
- Q4: поддерживаются внутренний и внешний Gateway; тестировать нужно на внешнем.
  Пользователь выбрал штатную авторизацию Hermes без дополнительной системы входа.
  Это принимается после сообщения о рекомендации upstream использовать password
  provider в доверенной сети/VPN, а OAuth/OIDC — для публичного интернета. В рамках
  этого расширения не добавляем внешний auth proxy, SSO или собственную форму входа.
- Q5: оба режима поддерживаются с явно документированной границей: разные пути
  одного домена не изолируют browser origins. Для недоверенных клиентов рекомендуются
  отдельные поддомены; Path предназначен для одной доверенной группы.
- Q6: DNS, TLS и Gateway готовит инфраструктура. Оператор создаёт Service, HTTPRoute
  и правила доступа к агенту, ссылаясь на готовый HTTPS listener. README описывает
  подготовку домена и wildcard. Последующим уточнением пользователь выбрал именно
  `agents.s2technologies.ru`, без `ext`; необходимые DNS/TLS готовит инфраструктура.

Эти продуктовые решения также зафиксированы в [ADR 0004](../adr/0004-optional-web-access.md).

## Согласованный инженерный контракт

Следующие детали подготовлены на основе принятых ответов и делегированного выбора
технических полей. Пользователь подтвердил переход к реализации; этот контракт ещё не является отчётом о готовой функции.

### Каналы и совместимость

`spec.telegram` становится необязательным: отсутствие означает выключенный Telegram,
присутствие требует прежние bot token и allowedUserIDs. Существующие CR сохраняют
поведение. `spec.web.enabled` по умолчанию `false`. Допустимы все четыре комбинации:

| Telegram | Web | Работа инсталляции |
| --- | --- | --- |
| Выключен | Выключен | Штатный gateway без пользовательских входов; cron и housekeeping продолжаются |
| Включён | Выключен | Прежний Telegram gateway |
| Выключен | Включён | Gateway без Telegram и штатный dashboard |
| Включён | Включён | Gateway с Telegram и штатный dashboard |

`spec.suspend` останавливает всю инсталляцию. Все режимы используют прежний PVC
с полным состоянием; изменения каналов не удаляют SOUL, skills, память, workspace,
историю или cron. Удалённый из CR Telegram не должен восстанавливаться из старого
config или оставшегося в Secret токена при следующем запуске.

### Адрес и Gateway

Секция `spec.web` содержит `enabled`, `routing`, `gatewayRef`, `auth` и `network`.
Основные поля адреса:

```yaml
spec:
  web:
    enabled: true
    routing:
      mode: Subdomain
      baseDomain: agents.example.com
      name: hermes1
    gatewayRef:
      name: external
      namespace: infra-gateway
      sectionName: https
    auth:
      username: admin
```

Это фрагмент контракта, не готовый CR: обязательные модель/storage и сведения
о входящем трафике указываются дополнительно.

- `mode`: `Subdomain` или `Path`; при включённом Web выбирается явно.
- `baseDomain`: hostname без схемы, порта и пути.
- `name`: один DNS-compatible сегмент, по умолчанию `metadata.name`; может отличаться
  для одноимённых CR в разных namespaces.
- `Subdomain` даёт `https://<name>.<baseDomain>/`, `Path` —
  `https://<baseDomain>/<name>/`. Полученный hostname также проходит DNS-валидацию.
- `gatewayRef` содержит имя, namespace и конкретный HTTPS listener;
  namespace при отсутствии — namespace CR. DNS и сертификаты оператор не меняет.
- Обнаруженный конфликт адресов между управляемыми инсталляциями отражается в status;
  чужой HTTPRoute не захватывается. Администратор отвечает за согласование маршрутов
  с другими приложениями на выбранном Gateway.
- В status публикуются вычисленный URL, HTTPRoute reference и состояние Web/route.
  Готовность маршрута требует актуальных `Accepted` и `ResolvedRefs` нужного parent;
  она не утверждает проверку внешнего DNS/TLS из интернета.
- Без Gateway API в кластере Telegram и режим без каналов продолжают работать.
  Включённый Web сообщает об отсутствующей зависимости, а не ломает весь оператор.

### Credentials и ротация

Используется штатный password provider Hermes. Логин задаётся `web.auth.username`,
default `admin`. В основном Secret находятся два отдельных ключа:

| Ключ | Назначение |
| --- | --- |
| `WEB_PASSWORD` | Пароль, который администратор получает из Secret и вводит на штатной странице входа |
| `WEB_SESSION_SECRET` | Случайный ключ подписи browser sessions; не используется как пароль |

Основной Secret выбирается существующим `credentials.secretName` или соглашением
`<имя>-hermes-secret`; cross-namespace references не добавляются. Значения не попадают
в CR, status, Events, логи или публичные примеры. Под получает credential snapshot
через существующий механизм ревизий; отдельный источник web credentials не вводится.

При включении Web оператор использует непустые существующие значения. Отсутствующие
ключи генерирует криптографическим генератором (не менее 32 случайных байт на ключ,
в текстовом представлении) и сохраняет с проверкой конкурентных изменений Secret.
При необходимости создаётся отсутствующий основной Secret только с web-ключами;
обязательные model credentials по-прежнему предоставляет администратор.
Остальные поля/ключи Secret и его владение не перезаписываются. Пустое значение
существующего ключа считается ошибкой, а не скрытой командой регенерации.

Рестарты, reconcile и выключение/повторное включение Web не меняют credentials.
Исходный Secret и web-ключи не удаляются при выключении Web или удалении CR.
Если Secret immutable либо полностью перезаписывается External Secrets/GitOps,
оба web-ключа следует предоставить через его владельца; конфликт описывается в status.

Ротация выполняется обычным обновлением ключей Secret и применением новой runtime
revision. Для смены пароля **с выходом всех ранее вошедших пользователей** меняются
оба ключа. Смена только `WEB_PASSWORD` изменяет последующий вход, но не отзывает
выданные upstream сессии. Удаление ключа при включённом Web вызывает генерацию нового
значения; для обычной эксплуатации предпочтительна явная замена. Пароль и ключ подписи
не ротируются по расписанию или при каждом рестарте.

### Запуск, сеть и отключение

Gateway и dashboard работают в одном Pod на том же home, под прежним non-root
securityContext и с теми же ограничениями ресурсов. Управляемый launcher запускает
нужные процессы после восстановления конфигурации; процессы и дочерний TUI корректно
завершаются при остановке. Probes проверяют живые процессы и только объявленные каналы.
Недоступность внешнего Gateway сама по себе не вызывает бесконечные рестарты Pod.
Upstream-код не изменяется; наличие готового web/TUI build проверяется на нашем образе.

Service и HTTPRoute публикуют только web port. В `web.network` задаются источники
входящего трафика от выбранного Gateway (ограниченные selectors/IP peers) и доверенные
proxy IP/CIDR. Примеры для Istio используют namespace и Pod selector совместно.
Gateway labels не считаются универсальными для всех контроллеров. Не создаётся
безусловное ingress-разрешение от всех Pod/адресов; существующий private-egress запрет
сохраняется. Автоопределение внешнего или внутреннего назначения по имени Gateway
не используется.

Для Path HTTPRoute снимает prefix перед backend и устанавливает согласованный
`X-Forwarded-Prefix`; forwarded metadata клиента не должна подменять управляемый
адрес или HTTPS. Проверяются правильные redirect, assets, API, WebSocket и Secure
cookies; `public_url` указывает полный внешний URL.

При выключении Web убираются HTTPRoute, web Service/port, разрешающий ingress и
dashboard. Состояние на PVC и исходные credentials остаются. Изменение адреса
удаляет прежнюю публикацию; ошибка новой web-конфигурации не должна незаметно
оставлять прежний URL открытым. При suspend внешняя публикация снимается,
при resume восстанавливается с прежними credentials.

## Приёмка и документация

1. API/config/controller tests: четыре комбинации каналов, совместимость старых CR,
   оба адресных режима, валидация, недостающий Gateway API/listener, conflicts и status.
2. Secrets: генерация и повторный reconcile, явные значения, отсутствие перезаписи
   других ключей, конкурирующее изменение, immutable Secret, ротация и отсутствие утечек.
3. Runtime: запуск dashboard/TUI на текущем image digest, gateway без каналов,
   Web-only и совместно с Telegram; non-root, probes, остановка и отсутствие второго poller.
4. Внешний smoke: штатная форма входа, отказ без credentials/с неверным паролем,
   рабочий чат с моделью через WebSocket, файлы и браузерная навигация. Для Path —
   загрузка assets, API, redirects, cookies и работа двух инсталляций в одном браузере
   без утверждения об изоляции origins.
5. Жизненный цикл: рестарты контейнера/Pod с прежними credentials и сохранностью данных,
   отключение/включение Web, смена URL, ротация обоих ключей с отзывом старой сессии,
   сохранение исходящей сетевой изоляции.
6. Обновить README, CR reference, install/operations/security, примеры всех режимов,
   получение и ротацию credentials, подготовку wildcard и требования Gateway API.
   Зафиксировать выполненные и не выполненные live-проверки отдельно.

Тестовая инсталляция — существующий `hermes-operator-test/hermes-smoke` в `berger-apps`;
её PVC и старый сохранённый PVC не пересоздаются. Gateway — `infra-gateway/external`.
По уточнению пользователя базовый домен обоих режимов — `agents.s2technologies.ru`,
без `ext`. Тестовые адреса:
`https://hermes-smoke.agents.s2technologies.ru/` и
`https://agents.s2technologies.ru/hermes-smoke/`.
Пользователь планирует изменить DNS, который на момент исследования направлял
эту зону на внутренний Gateway. Для Path подходит существующий HTTPS listener `https`
с сертификатом `*.s2technologies.ru`. Для Subdomain требуется сертификат
`*.agents.s2technologies.ru` и HTTPS listener внешнего Gateway, обслуживающий его;
существующий сертификат родительской зоны вложенные имена не покрывает.
Перед live-тестами повторно проверяются DNS, выбранный listener и TLS обоих адресов.
Namespace теста понадобится разрешающий label `gateway.berger.dev/external: "true"`.
Для проверки нескольких web-инсталляций второй Telegram token не нужен; используется
временная Web-only инсталляция со своим PVC. Любые Telegram-проверки ограничены
ранее разрешённым пользователем ботом `@HermesOperatorK8SBot`.
