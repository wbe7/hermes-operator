# Проектирование Hermes Operator

Статус: продуктовые решения согласованы; пользователь подтвердил продолжение после завершения вопросов. [Спецификация v1alpha1](v1alpha1.md) фиксирует инженерный контракт, [план](../superpowers/plans/2026-09-18-hermes-operator.md) — порядок реализации. Runtime-совместимость ещё не подтверждена испытаниями.
Дата начала и обновления: 2026-09-18.

## Принятые требования

| Ветвь | Решение пользователя |
| --- | --- |
| Q1. Продукт | Самостоятельный хорошо документированный Kubernetes-оператор. Внешние frontend/backend находятся за пределами проекта. |
| Q2. Полномочия | CR и Secrets создаёт namespace admin или другая сторона с явно выданными правами. Конечный пользователь их непосредственно не создаёт. |
| Q3. Изоляция | Максимально использовать стандартные механизмы Kubernetes; Kata/gVisor и аналогичные обязательные усложнения исключены. |
| Q4. Credentials | Ключи выделены конкретному пользователю/инсталляции; прочитать их изнутри допустимо. Общего ключа клиентов не будет. Требуется удобное соглашение об имени Secret с возможностью явного ref. |
| Q5. Hermes | Оригинальный код без изменений; официальный образ предпочтителен. Своя сборка допускается при отсутствии официального образа. Невозможность выполнить требование без patch требует отдельного обсуждения. |
| Q6. Сеть | Публичный интернет открыт полностью. Приватные назначения закрыты, кроме явно разрешённых конкретных IP. |
| Q7. Хранение | Сохраняется всё состояние: workspace, skills, память, сессии и прочие рабочие данные. С учётом последнего уточнения runtime config writable, а параметры CR восстанавливаются при запуске. |
| Q8. Каналы | Первый релиз — только Telegram. Веб-интерфейс и HTTPRoute отложены. |
| Q9. Telegram | Обязательный сценарий — личные сообщения. Группы допустимы как простое отдельно настраиваемое расширение; если это усложняет первый релиз, отложить. |
| Q10. Удаление | Созданный оператором PVC сохраняется по умолчанию, явный режим Delete удаляет его. Подключённый существующий PVC оператор не удаляет. |
| Q11. Обновления | Допустим автоматический перезапуск после изменения CR, используемого Secret или версии Hermes, с возможным прерыванием текущего запроса. |
| Q12. Полнота API | Принят комбинированный API: все основные настройки — типизированные поля основного CR, остальные настройки — дополнительный объект Hermes config. Требуется подробная документация. |
| Q13. Область работы | Одна установка оператора сразу обслуживает весь кластер. |
| Q14. Backup/restore | Не входит в первую версию; вернуться к этому отдельно позднее. |
| Уточнение персонализации | SOUL, личность, пользовательские инструкции и первичная настройка агента под себя доступны пользователю внутри агента. Оператор не должен делать их read-only или затирать при reconcile. |
| Уточнение восстановления | Runtime config может быть writable, включая модель. При следующем запуске восстанавливаются значения из CR/Secrets; всё пользовательское состояние остаётся на PVC. |

Версия Hermes, модель, reasoning, Telegram и правила доступа задаются декларативно. Секретные значения находятся в Secrets, а не в CR. Оператор создаёт ресурсы запуска и конфигурацию. Параметры persistent storage задаются через CR. В репозитории нужны средства установки оператора и документация.

Последнее уточнение пользователя заменяет первоначальное требование immutable runtime config: пользователь может менять работающий Hermes, а значения из CR/Secrets восстанавливаются при следующем запуске. SOUL, skills, память, workspace и личные настройки сохраняются; Kubernetes-изоляция действует независимо от runtime config. См. [уточнённый ADR](../adr/0001-declarative-configuration-authority.md).

## Соглашение о Secret

Выбор имени делегирован разработчику. При отсутствии явной ссылки инсталляция `maria` использует Secret `maria-hermes-secret` в своём namespace. Явная ссылка позволяет выбрать другое имя; cross-namespace Secret references не планируются.

Secret предоставляет администратор или внешний backend. Оператор не может самостоятельно получить Telegram bot token или API key провайдера и не генерирует фиктивные значения. Если обязательный Secret или ключ отсутствует, новый агент ждёт зависимость с понятным status. Имена полей и ключей зафиксированы в спецификации v1alpha1; API ещё не реализован и не опубликован.

## Технические проверки и детализация

| Ветвь | Что требуется решить или проверить |
| --- | --- |
| Восстановление upstream config | Проверить startup merge CR/Secrets в writable home, обработку session model overrides без потери истории и non-root запуск официального образа. |
| Telegram | Проверить явный запрет групп и стоимость отдельного opt-in; один bot token на инсталляцию; polling и sender allowlist. |
| Persistent storage | Создание PVC и подключение существующего; разделение workspace/home; resize и явное повторное подключение сохранённого PVC. Backup/restore исключены из первого релиза. |
| Обновления | Время на остановку, диагностирование неудачного обновления, отсутствие штатного запуска двух polling consumers. |
| Полнота конфигурации | Зафиксировать список основных полей CR, mapping в upstream, конфликты extraConfig, валидацию и поддерживаемые версии. |
| Развёртывание | Cluster-wide watch и RBAC контроллера; namespace-local зависимости агентов; Helm; обязательный CNI с NetworkPolicy enforcement; DNS и сеть кластера. |
| Эксплуатация | Ресурсы, планируемый масштаб, suspend, readiness/status, метрики, тестирование и критерии первого релиза. |

Эта таблица фиксирует техническую работу, выявленную интервью. Поля, defaults и поведение выбраны в спецификации; способы запуска требуют runtime-проверки. Исследование не заменяет проверку совместимости конкретного официального image digest.

## Следствия второго раунда

- Retention PVC не является резервным копированием; решение об удалении PVC отдельно от reclaim policy underlying PV.
- Один агент имеет общий workspace и состояние для всех разрешённых пользователей; отдельная пользовательская изоляция внутри одной инсталляции не проектируется.
- Обновление включает остановку прежнего процесса перед новым запуском с ограниченным временем на завершение. Сохранённое состояние переживает рестарт; завершение текущего запроса не гарантируется.
- Дополнительный config не дублирует основные поля, не переопределяет операторские пути/credentials/ограничения доступа и не отбирает пользовательскую персонализацию. Конфликт отклоняется явно; поддержка параметров зависит от версии Hermes.
- Список базовых полей и правила API описаны в [спецификации v1alpha1](v1alpha1.md) перед реализацией CRD.

## Итог третьего раунда

Приняты cluster-wide работа и отсутствие backup/restore в первом релизе. Контроллер может находиться в служебном namespace; пользовательский агент не получает его cluster-wide права. PVC retention сохраняет данные, но не создаёт резервную копию.

Финальное уточнение пользователя отменяет read-only runtime config и managed overlay. CR задаёт эталон для каждого запуска; пользователь свободно персонализирует агента и может временно менять его модель и другие настройки. Восстанавливаются управляемые параметры, а не весь home.

Проверка startup merge, Telegram-фильтров, non-root образа, персональной настройки и storage mounts — технические предпосылки, а не новые вопросы к пользователю. Если исходный образ не сможет выполнить согласованный контракт без изменения upstream, это будет вынесено на отдельное обсуждение.
